# DC3 Decomp - Claude Context

Dance Central 3 decompilation for Xbox 360 (PowerPC). Goal: produce matching assembly from C++ source.

The target binary in `orig/` is a debug build pulled from an Xbox 360 dev unit (not retail). This means no link-time optimization (LTCG) - matching should be achievable for most functions.

## Key Commands

```bash
ninja                              # Build and regenerate report.json
scripts/measure_progress.sh --functions --detailed HEAD  # Progress vs commit
scripts/measure_progress.sh --current-dir /path/to/worktree HEAD  # Worktree vs commit
scripts/clean_stale_objects.sh     # Fix stale .obj files (older than PCH)
scripts/dc3-agent-test.sh          # Launch native port with HTTP debug server + fast boot + telemetry
# Re-sync decomp.db after permuter wins land on main (run from repo root, ~2-3 min):
python3 scripts/sync_match_percent.py --build --promote   # rebuilds report.json + updates current_percent/verdict
```

To interact with a running native engine instance, use `scripts/dc3-agent-test.sh` (sets `DC3_HTTP=1 DC3_FAST_BOOT=1 DC3_TEL=1`). Then `curl localhost:9090/api/health`, `/api/dta/eval`, `/api/screenshot`, etc. See `docs/tools/HTTP_DEBUG_SERVER.md`.

Check `./docs/tools/INDEX.md` for agent tool selection and `./docs/INDEX.md` for the full docs sitemap.

## Orchestrator MCP Tools

Use the `mcp__orchestrator__` tools for all decomp analysis. **Reach for `bin/objdiff-cli` only for the cases named below** — and if you find another, that is a tooling gap worth closing, not a rule worth quietly breaking. (The old blanket "do not call `objdiff-cli` directly" was unfollowable: a transcript sweep — `scripts/orchestrator/transcript_cli_sweep.py`, re-run it — finds **2,722 real direct invocations** across 16,661 session files, ~534 of them DC3-scoped, reaching for `--include-data` and `--batch` among others: capabilities the wrappers did not have. Gaps closed 2026-08-19; the honest exceptions are named rather than denied. Full table: [docs/tools/REFERENCE.md](docs/tools/REFERENCE.md#objdiff-cli-through-mcp-what-maps-to-what).)

**Still legitimate direct `bin/objdiff-cli` use** — do not "fix" these:
1. **Build/measurement infrastructure**: the ninja `report generate` rule, `tools/none_guard.py`, `tools/project.py`, `scripts/measure_progress.sh`, `scripts/sync_match_percent.py`. These *are* the measurement layer; routing them through MCP would be circular.
2. **Another repo.** `run_objdiff` raises `CrossProjectError` for a foreign `project_dir` deliberately — use that repo's own orchestrator, or its CLI.
3. **`-1/-2` on genuinely arbitrary object pairs** (`-1 $TGT -2 $TGT` to read the target's own listing; a saved candidate `.obj`), plus `doc-links` and `report query`. If you only wanted to skip a rebuild, that is now `build=false`.

- `run_objdiff` — build + diff a function, returns match%, verdict, enrichment. Source of truth for decomp percentages. **Always pass `project_dir`** when working in a worktree; omitting it silently measures the main repo and your edits look like they did nothing.
  - `include_data: true` diffs the DATA section — vtables (`??_7`), RTTI (`??_R*`), pointer/jump tables, string pools, static initializers — and renders each pointer slot with the symbol each side resolves it to. No-op on code symbols. Data symbols usually need `unit` naming the object that *defines* them (an undefined external answers "Symbol not found in target").
  - `diff_mode` picks the **relocation ruler**, and there are three. `normalized` (default, `=none`) scores code shape only and hides wrong-callee bugs entirely — `KinectShareConnection::Poll` reads 100.0% with **0** mismatch rows there. **`name_check` is the wrong-callee ruler** (it charges relocation *names*, and is `report.json`'s ruler): on that same function it finds **1** row, a real `MakeString<unsigned char>` vs `MakeString<char>` divergence. `raw` (`=all`) also charges *addends* — it is the addend view, and over a 14-function sample **995 of the 997 rows it added over `name_check` were noise** (same symbol at a different address, `lbl_*` vs a named static, or register-only). Reach for `name_check` to hunt a wrong callee; reach for `raw` when you actually care about addends.
    - ⚠ Why omitting `-c` is *not* raw: **not** because "the fork's default is normalized" — that explanation was wrong and is retracted. objdiff-cli's own default is `DataValue`, a third ruler with a third row count (147 on `CamShot::Load`, vs 119 for `none`/`name_check` and 151 for `all`). Omitting the flag lands on `name_check` because **this repo's `objdiff.json`** sets `"functionRelocDiffs": "name_check"`. The behaviour travels with the **project config, not the binary** — which matters because `bin/objdiff-cli` is a symlink shared with `../rb3` and `../rb3-xenon`.
    - ⚠ `run_diff_inspect(diff_mode="raw")` before 2026-08-19 was **mislabelled, not blind**: it silently measured `name_check`. Conclusions drawn from it were made with a sharper-than-`none` ruler, but they never counted addends. (Unrelated: the `Match: 100.0% normalized (99.8% raw)` strings are `raw_match_percent`, a different axis.)
  - `output_format: "json"` returns objdiff's raw JSON. Use it instead of shelling out to parse the JSON yourself.
  - `build: false` diffs already-built objects without running ninja — fleet-safe, and the answer is then about the tree as last built.
  - ⚠ **`project_dir` selects a *worktree of this project*, never a different project.** These tools are pinned to DC3's `decomp.db`, `report.json`, struct DB and title ID (`373307D9`). Pointing `project_dir` at a foreign repo — `../rb3-xenon`, `../rb3` — used to answer out of DC3's database and return a plausible wrong number (2026-08-04: 93.3%, DC3's baseline, where rb3-xenon's was 92.2%; and DC3's `ObjectDir::Iterate` 100.0% where rb3-xenon's is ~60%). **Since `2d39e6cc` (2026-08-04) this raises `CrossProjectError`** naming both paths and both title IDs — it can no longer answer silently. To work in another decomp tree, use that tree's own orchestrator (`<repo>/scripts/orchestrator/mcp_server.py`). Note the DB-only tools (`query_functions`, `get_attempts`, `lookup_struct_offset`, `lookup_merged_symbol`) take no `project_dir` and are *always* about DC3.
- `run_symbol_sweep` — **many symbols in one call**; the shape a per-symbol diff cannot express, and the reason agents wrote their own loops. `kind="vtable_slots"` reproduces the published vtable adjudication over the whole binary (~2,900 diffs, ~3 min at 16 workers); `kind="data_symbols"` takes any symbol glob; `kind="functions"` batch-diffs a symbol list through one objdiff process. **Every sweep states its denominator** — universe, examined, and each drop reason — and a `max_symbols` truncation is labelled `TRUNCATED` rather than presented as a total. Read-only: no ninja, no `decomp.db` writes, safe alongside the fleet.
- `run_diff_inspect` — deeper analysis: `diagnose` (root cause), `mismatches` (instruction table), `clusters`, `regswaps`, etc.
- `run_analyze_function` — combines objdiff with struct offset resolution for field-level mismatch context.
- `query_functions` — find workable functions by unit pattern and match range. A work-selection index, not a measurement: `current_percent` drifts (the ninja DB sync deliberately does not write it). **For objdiff pattern classes, do not read a `has_*` column — pass `objdiff_pattern=`**, which joins the measured `function_patterns` table so a row only appears if a scan under that ruler actually examined it. `objdiff_pattern` with `pattern_ruler='none'`, or with no scan recorded for the ruler, **raises** rather than returning an empty set that reads like an exhausted class. `has_assert_revs`/`has_ltcg_pooling` were dropped. Re-measure with `run_objdiff` before acting — see `docs/tools/REFERENCE.md`.
  - ⚠ **The `has_*` pattern columns are a legacy surface with a provenance column.** The 2026-08-19 repair (`scripts/backfill_reloc_patterns.py --apply`) was correct about the cause and wrong about the numbers, and `--apply` there now refuses.   - **The five callee classes, whole binary, `name_check`, objdiff 4.2.8** (**scan id=8** @ `95639cf5c`; **48,290 of 48,328** report.json functions examined, all 38 drops `objdiff-not_found`): `LINKER_MERGED` **2** (not 1310 — that number was an over-broad detector, the wrong ruler and an unsettled tree, all at once), `WRONG_CALLEE` **81** and `TEMPLATE_INSTANTIATION_MISMATCH` **5** (both `LikelyFixable`, and both were hidden inside the old LINKER_MERGED bucket that told agents to give up on them), `REGISTER_SAVE_HELPER_MISMATCH` **208** (set-identical to `PROLOGUE_MISMATCH`, so `has_prologue_mismatch` is kept and RSH gets no column), `UNVERIFIABLE_CALLEE_NAME` **0** (structural — the graded ruler exempts placeholder names before the detector runs; it can only fire under `all`). ⚠ **These counts move as work lands — re-derive rather than quoting them.** The class is being actively worked: scan 6 (2026-08-22) read 113 / 15, scan 8 reads 81 / 5, and the drop is real fixes plus the `icf_aliases.map` widening in `95639cf5c` (8,719 → 8,843 memberships), which reclassified 16 rows that were never source bugs. The **4.2.6** figures this bullet used to carry (4 / 127 / 18 / 219, denominator 48,325) are superseded, and that drop too is **source movement, not a vocabulary change** — established rather than assumed, by running the full census with 4.2.7 and 4.2.8 over the *same* tree and objects: **0 of 48,290 rows differ**. So: `callee_gate.ensure_current_scan()` **raises `StalePatternScanError`** when the recorded scan's `tool_version` disagrees with the installed binary (also on no scan at all, `tree_verified = 0`, or a version string carrying no `xxh3`), and `pattern_census.py` reads `--version` **uncached** before *and* after the sweep, refusing `--apply` and exiting 5 if they disagree. `python3 scripts/verify_pattern_scan_current.py --check` is the ~0.1 s standalone assertion, and **it must now be able to say which of four things is wrong** — it used to report *"no pattern scan recorded"* for two conditions that are not staleness at all. ## Code Style
- Be carefuly when modifying MILO_ASSERT() calls or OBJ_MEM_OVERLOAD macros. Whatever is in there should be tested carefully.
- Keep members protected/private unless confirmed public via DWARF or asserts. For external access, add getters/setters rather than making members public. Use friend classes for closely related types (e.g., Foo and FooHandle).

## Known Patterns
- **A displayed "100.0%" is NOT byte-identity** — but know *which* surface you are reading. `decomp.db.current_percent` rounds (inconsistently: it holds `99.85558` for one row and `95.38` for another), and `run_objdiff`'s headline rounds (it printed `Match: 100.0% normalized` above a table listing 3 mismatches). **`report.json.match_percent_normalized` does NOT round** — it is an exact score-weighted f32, and an **immediate or displacement** diff costs a point that survives normalization, so a wrong field *that is encoded as an offset or a constant* is always visible there (`CamShot::Load` = `99.85558`; a re-injected single-field bug = `99.992905`). **That guarantee does NOT extend to a wrong callee.** Relocation penalties are folded into `arg_diff_score` by design, and `match_percent_normalized = diff_score − arg_diff_score` (objdiff-core `src/diff/code.rs:1626-1641`), so calling an entirely different symbol used to cost exactly **zero** normalized points under *every* `functionRelocDiffs` setting including `name_check`. **FIXED 2026-08-20 in the objdiff fork, released as `v4.2.4`** (refined by `v4.2.5`; both tagged and pushed): under `name_check` — and only there — a *vetted* relocation-name disagreement now stays in `diff_score` instead of being folded into `arg_diff_score`, so it reaches `match_percent_normalized`. **Require `objdiff-cli --version` ≥ 4.2.5** before trusting a canonical number for this class — the version string carries the git hash, which is a far better check than the mtime advice further down this bullet. The fold's justification ("reloc diffs are dominated by benign noise") was measured under the other modes; `name_check` exists precisely to strip that noise first. Three noise classes are still folded, each **measured rather than assumed**: register save/restore helpers (`__savegprlr_25` vs `_26` is regalloc, and normalization forgives regalloc), placeholder-named enclosing symbols (`fn_<addr>` EH funclets are paired BY BYTE SIGNATURE — one pair was `RndRibbon`'s static guard against `RndFont`'s), and function-local-static scope ordinals (`?BD@` vs `?BH@`, a per-TU counter). Whole-binary A/B over the same prebuilt objects: 328 functions drop, **0 rise**, 54 leave the matched set (19,288 B), headline **-0.1117pp**, and `fuzzy_match_percent` is byte-identical on all 48,344 functions (the built-in control). Of those 54, **52 have a real charged site and 0 are charged on noise alone**. ⚠ The three sibling repos (`rb3`, `rb3-xenon`) also set `name_check` and share this binary by symlink. Measured 2026-08-19: repointing all 13 `bl` sites of a 100%-matched function at a nonexistent decoy, changing zero instruction bytes, left normalized at `100.0` and `run_objdiff` at 64 equal / 0 mismatches; a real `extern "C"` mangling bug in `EQEffect::SetParameter` was invisible the same way, moving only `fuzzy_match_percent`, by 0.028, on 1 function of 48,344. **508 named functions (433,788 bytes) carry at least one relocation-name charge** (graded `fuzzy` < relocation-blind `fuzzy`), of which **42 (17,084 B) are otherwise perfect** — on those, closing the name crosses the row and pays its full size. ⚠ The earlier figures (198/37,496, and a re-derived 186/32,388 = 73 named + 113 `fn_`/`lbl_` funclets) counted **only** the otherwise-perfect slice; that is a reporting slice, not the population, and it hides ~92% of the class — including the `createFilter` bug itself, which sits on a row that is 84.7% under the blind ruler. To see wrong callees, `match_percent_normalized` is now sufficient **provided the report was generated by a binary containing the 2026-08-20 fix** (check `bin/objdiff-cli`'s mtime — nothing rebuilds it for you); otherwise read `fuzzy_match_percent`, `report_raw.json`, or run `scripts/analysis/reloc_name_gate.py` (lists the population with linker-map addresses for both names, checks the config against the map first, and ships a `--selftest` negative control). **Check the instrument before believing a row**: three of the loudest findings in that population were config defects, not source bugs — one config symbol 0xA0 off its map address made `MirrorJoint` read as indexing the joint-PARENT table, and all twelve `RndShader` globals were named one slot early. See [docs/decomp/patterns/relocation-names-are-unmetered.md](docs/decomp/patterns/relocation-names-are-unmetered.md). What normalization *also* forgives is register permutation, so `100.0` there means "no non-register, non-relocation mismatch", not "byte-identical". The standing rule "a behavioral divergence on a 100%-matched function must be a harness artifact" **may only be applied to a zero-mismatch instruction count, never to a displayed number** — two real bugs were hiding under a displayed 100.0 (`CharUpperTwist::Load` Save/Load member-order permutation, `RndFlare::Load` reading the wrong field). See [docs/decomp/patterns/rounded-100-hides-real-bugs.md](docs/decomp/patterns/rounded-100-hides-real-bugs.md).
- **`objdiff-cli diff` and `objdiff-cli report generate` were TWO DIFFERENT RULERS, and the per-function one read LOW.** The two entry points carry different *hardcoded base configs*, neither of which is the schema default: `report generate` (`objdiff-cli/src/cmd/report.rs:581`) sets `functionRelocDiffs=none, combineDataSections=true, combineTextSections=true, ppc.calculatePoolRelocations=false`; `diff` (`diff.rs:1070`, and `--batch` at `diff.rs:1807`) sets only `functionRelocDiffs=data_value` and leaves the other three at schema defaults (`false / false / **true**`). Both then layer `objdiff.json`'s `options`, which used to pin only `functionRelocDiffs` — so the two agreed on the ruler they argue about and disagreed on three others. `ppc.calculatePoolRelocations` is the one that bites: it **synthesizes** `R_PPC_NONE` "fake" relocations for pooled data loads (`objdiff-core/src/arch/ppc/mod.rs:819 make_fake_pool_reloc`; the schema literally calls them fake), reconstructed per object from *that object's own symbol table* — and a dtk-carved target obj and our MSVC COMDAT obj do not reconstruct the same set. `reloc_eq` (`objdiff-core/src/diff/code.rs:1338`) charges a **target-only** relocation under every ruler except `none`, `name_check` included, so the charged row can be two *textually identical* instructions: `?SetVHBlurWeights@@YAX_NHH@Z` read `100.0` in report.json and `99.675674` through `run_objdiff`, whose one mismatch was `subi r28, r11, 0x8` vs `subi r28, r11, 0x8`. **Whole-binary sweep 2026-08-31** (one worktree, cold report cache, `diff --batch` over all 48,339 names): **155 functions / 120,728 B scored LOWER by the per-function path, 0 scored higher**; **49 of them (28,240 B) read exactly 100.0 in report.json and <100 through `run_objdiff`** — every promotion refused on that basis was refused wrongly; 74 of the 155 carry an `AT_LIMIT` verdict taken over a row set containing 247 phantom rows. ⚠ **The headline is NOT overstated by this** — the report path was never the lower of the two. **FIXED** by pinning all four keys in `tools/project.py`'s `options` block (both entry points layer it, so no tool rebuild and no MCP restart); **no recorded number moved** (29,902 / 5,056,848 / 44.45998% / fuzzy 54.37279 before and after) and the re-sweep leaves 0 config-caused disagreements. This is *upstream* objdiff behaviour (`0c9e552`, 2025-05-07, report.rs only), so **`../rb3` and `../rb3-xenon` have it too**. Guard: `python3 scripts/verify_ruler_agreement.py --check` (~0.2 s) and `--selftest` (flips the knob back and *requires* failure; exits 5 "vacuous" rather than passing on an empty probe). ⚠ `scripts/analysis/ruler.py` already knew this and is imported only by `scripts/analysis/*` — never by the MCP tools every lane actually calls, which is why a correct doc plus a correct unused helper enforced nothing. Full write-up + both controls: [docs/decomp/patterns/two-objdiff-entry-points-two-rulers.md](docs/decomp/patterns/two-objdiff-entry-points-two-rulers.md).
- **`run_objdiff`'s "Offset Mismatches (resolved)" block ignores the base register** — it resolves any offset against the class struct, so a pure `(r1)` stack-slot diff is rendered as *"Source accesses 'X' but target accesses 'Y' — wrong field?"*, indistinguishable from a true positive. It manufactured exactly that story for `FxSendChorus::Load` and sent a lane hunting a nonexistent missing member in `FxSend`. Treat that block as a lead, never a finding, and read the prologue first.
- **A unicorn verdict is only as good as the harness that produced it**: `unicorn_signal_version` describes the *comparator*, not the *emulator*. Eight harness defects fixed 2026-08-18/19 changed verdicts wholesale without touching one comparator rule, so signal_version sat at 3 across the break and the old numbers overstated real bugs ~8x. Read `unicorn_harness_version` (h1..hN, changelog in `scripts/unicorn_runner/signal_version.py`); **h1/NULL means pre-fix, do not trust**. Filter with `query_functions(min_unicorn_harness_version=4)` or `scripts/unicorn/query.py --min-harness 4`. After the 2026-08-19 whole-DB re-ingest, **99.4% of DIVERGENT rows are in a known-artifact class** (`data_layout` alone is 9,815 of 12,419) and there are **zero `error`-class rows** — the oracle is now a regression detector, not a bug finder. See [docs/analysis/2026-08-19-unicorn-reingest.md](docs/analysis/2026-08-19-unicorn-reingest.md).
- **Unsigned zero comparisons**: Use `x > 0` instead of `x != 0` for unsigned types (generates `ble` vs `beq`)
- **Merged symbols**: `merged_<addr>` names indicate Identical COMDAT Folding (ICF) where the linker merged functions with identical machine code to a single address
- **Automatic header tracking**: Ninja tracks all header dependencies via `/showIncludes` + wibo path rewriting. Touching any header automatically rebuilds only the affected .obj files. No manual `touch` needed. **Except for the 178 headers that come in through the PCH — see the next bullet.**
- **A PCH-reached header has NO per-TU dependency record. Run a full `ninja` for any experiment that edits one.** 574 of the 956 TUs compile with `/Yu"decomp_pch.h" /FI"decomp_pch.h"`, and MSVC deliberately omits every PCH-contained header from `/showIncludes`. Measured 2026-08-19: `ninja -t deps build/373307D9/src/system/obj/TypeProps.obj` records **9** headers (**10** on 2026-08-31), **none** of them `ObjPtr_p.h`, `obj/Object.h` or `os/Debug.h`; a non-PCH TU (`src/lazer/game/Game.obj`) records **492**, `ObjPtr_p.h` among them. The only thing that makes a per-target build correct today is the explicit `build/373307D9/pch/system.pch` implicit input on those edges — all 574 currently carry it, so `ninja <one>.obj` *does* rebuild the PCH and the object. That is a single generator detail with no independent check, and it does not hold in a worktree whose `.ninja_deps` has not been primed. **A spelling experiment that concludes "three spellings compile identically" is worthless if it was run per-target on a cold or mis-wired tree — use a full `ninja` and keep a negative control that is supposed to change the bytes.**
  - ⚠ **The control this bullet used to cite was vacuous, and the conclusion it supports is nevertheless true — both halves stated, because only one of them was ever evidenced.** The old wording was *"verified with a control: gutting `ObjPtrList::remove` to `return target == 0;` and rebuilding only `TypeProps.obj` changed the object's hash."* Until `ee8902a22` (2026-08-31) **every** MSVC recompile changed **every** object's bytes — COFF `TimeDateStamp` and the CodeView `S_OBJNAME` signature, both clock-derived — so "the hash changed" was true no matter what the edit was, or whether there was an edit at all. It remained true for a **per-target** build until 2026-08-31: `obj_build_metadata_patcher.py` was only a `post-compile` edge keyed on `all_source`, so `ninja <one>.obj` produced a *raw*, un-normalized object whose bare sha256 was clock-noise. Measured in a worktree at `ee8902a22`, `TypeProps.obj` rebuilt twice with **no source edit at all**: raw `efab4e23…` then `24dbd724…`; reproduced later the same day as `dfeda314…` / `e14ac6e8…`.
    - ✅ **CLOSED.** The metadata pass now also runs **inside** all three MSVC compile rules (`msvc`, `msvc_pch`, `msvc_pch_create`), chained with `&&` so a failure fails the compile edge. `config.obj_postprocess_cmd` in `configure.py` → `tools/project.py`. Measured in the fixing worktree, `TypeProps.obj`, `touch`-and-`ninja <one>.obj` ×3 with no source edit: `b59b971ec24a72bc` all three times, `TimeDateStamp=0x00000000`. Non-vacuous in the other direction on the same tree: appending one function moved it to `d8471eab…`, reverting returned it to `b59b971e…` exactly. Sabotage control — strip the `&&` clause from build.ninja's three rules and the same experiment gives `c892e9a2…` / `6cf873ef…` / `05354597…` with `TimeDateStamp=0x6a95a2e7,ea,ec`. ⚠ **The stamp has 1-second granularity**, so two per-target builds finishing inside the same second agree *even when unwired* — a quick two-shot repro can accidentally look deterministic. Put a `sleep 2` between runs, or read the timestamp field directly.
    - The wiring is guarded: `scripts/verify_objs_patched.py --check-compile-edge` (in the `post-compile` verify edge, before `--check`) parses `build.ninja` and fails if any of the three rules stops running the pass. It parses rather than greps on purpose — the post-compile `run_script` step names the same script, so a whole-file substring check would be green on a completely unwired tree.
    - **A per-target object is byte-STABLE, not fully PATCHED.** The other five passes still do not run on `ninja <one>.obj`; that is the older gap, and `scripts/verify_objs_patched.py --verify-manifest` is what detects a tree left in it. For a fully patched single object use `scripts/obj_patch_chain.py --apply --unit <rel>`. Comparing two *raw* objects errs in the safe direction: the five passes are deterministic functions of the object's own bytes plus the fixed target object, so raw equality implies patched equality, while raw *inequality* can in principle collapse to patched equality (an anon-namespace hash both sides get overwritten with). An inertness claim is therefore sound; a "my edit did something" claim from raw bytes can over-fire.
    - Sabotage-tested in `tests/test_objs_patched.py` (28 cases) with the mutation harness `tests/sabotage_objs_patched.py` — **25 of 25 deliberate defects detected**, including "the compile-edge check is a whole-file grep" and "`tree_sha256` hashes the hashes without their paths".
  - **Re-established 2026-08-31 with a control that can fail** (worktree at `ee8902a22`, full `ninja` first, then per-target rebuilds; each object hashed with the two clock fields zeroed via `obj_build_metadata_patcher.plan()`/`.normalize()`, which is exactly what the post-compile pass writes):

    | step | masked sha256 | reading |
    |---|---|---|
    | full `ninja` baseline | `d94966b59df76a0f` | patchers ran, `n_masked=0` |
    | per-target rebuild, **no edit**, ×2 | `d94966b59df76a0f` both | masked hashing is a real signal; raw differed both times |
    | gut `ObjPtrList::remove` (PCH-reached), `ninja <one>.obj` | **`e9642923383cf8b3`** | **the PCH-header edit propagates** |
    | revert, `ninja <one>.obj` | `d94966b59df76a0f` | reverses cleanly |

Both full builds of that worktree reported the same `tree_sha256=ef18cb39817d18d0`, so the `ee8902a22` fix reproduces outside the tree it was developed in.

Before quoting either, run `python3 scripts/verify_objs_patched.py --check-compile-edge` (~0.1 s): it is the assertion that the per-target path is still normalizing rather than measuring the wall clock. Same-path only, in both cases: MSVC writes the source path into `S_OBJNAME`'s name field, so two *worktrees* legitimately disagree and `tree_sha256` is not comparable across them.

Enumerate the current set with `ninja -t deps build/373307D9/pch/decomp_pch.obj`.

No edge names the objects, nothing stats them, and `report.json`'s `provenance` block does not describe them. Their content depends on `config/<v>/symbols.txt` (dtk names each function from it), so a report over objects split from a different symbols.txt is a different measurement — and silent, because a function whose target-side name no longer pairs scores `0.0`, indistinguishable from unwritten. **Measured 2026-08-21**, one worktree, one objdiff-cli (`4.2.7`/`76c8da87e040`), report cache **cold on both runs**, identical symbols.txt on disk: a report started 2 s into the split read **29,497**; the same command after it finished read **29,838**. A 341-function gap discriminated only by timing. Split ≈11.6 s, cold report ≈6 s, and several lanes build at once. ⚠ **This REFUTES the "stale `report.cache`" reading of the same gap** — `ReportCache::hash_unit` hashes the whole target obj, verified directly (one mutated symbol-name byte turns `1 hit/0 misses` into `0 hits/1 miss`) and end-to-end in both directions with a warm cache (`1,377 hits/847 misses`, correct number each way). Do not change the objdiff cache for this. - **No cargo depfile**: the `cargo` rule (only emitted if `--dtk`/`--objdiff` point at a *source dir*; this repo defaults to the prebuilt `../jeff` / `../objdiff` binaries, so no cargo edges exist) intentionally has no depfile — cargo's depfile uses an absolute target path that ninja rejects, making the tool perpetually dirty and re-firing CARGO (and potentially a re-SPLIT cascade) on every build. If you ever build the forks through ninja, `.rs` edits need `touch ../jeff/Cargo.toml && ninja` (dtk) or `touch ../objdiff/Cargo.toml && ninja` (objdiff-cli). Rebuilding a fork manually with cargo still works as before — ninja tracks the prebuilt binary's mtime. Same fix as rb3-xenon (2026-06-30).

If an upstream fix "isn't showing up", check the binary's mtime first.

A routine `cargo build --release` from `main` would have produced a dtk without it, and the next split would have rewritten all 2,223 objects into a different baseline. **Nothing would have caught it**: the objects are an undeclared build output, and `symbols.txt` is unchanged so the split-currency guard stays green.
  - **Closed**: `comdat-gap-boundary` is merged into jeff `main` (`76b4223`, merged from a throwaway worktree so the live checkout was never disturbed), byte-identity proven on **2223/2223 `.obj` and 2223/2223 `.s`** across three independent splits before the binary was replaced, and the redeploy left dc3 at **29,860 / 5,039,932 / 44.313232% — unchanged**, with objdiff's own report cache reporting **2224 hits / 0 misses** as independent confirmation. Deployed dtk is now `2b1e17b`. Old binary backed up at `/home/free/tmp/dtk-deployed-2026-08-18.bak`.
  - **`dtk --version` used to lie; it no longer does, and it can now say "unknown".** It reported `1.14.0 b4b25bcb4805…` — a commit that did *not* contain the code in the binary — because it was built from a dirty tree a minute before `b4b25bc` landed. It now prints an xxh3 of the running executable alongside a `-dirty`-suffixed commit, matching objdiff's format: `dtk 1.14.0 (2b1e17b137a5…, xxh3 a83e472cd047f3ad)`. **Trust the xxh3, not the commit stamp** — the stamp remains advisory (cargo watches mtime, not content, and a tracked file outside `src`/`Cargo.*` can differ from HEAD with no marker), and `build.rs` says so rather than implying otherwise. `split_manifest.json` records the hash too (MANIFEST_VERSION 2).
  - **The general rule, which cost two lanes to learn:** a version string is only provenance if it can report *"unknown"*. `objdiff-cli --version` carries a git hash **and** an xxh3 of the executable, which is why `callee_gate` and `pattern_census` can refuse a scan taken by a different binary. Anything without a content hash is a claim, not a measurement — verify by content (`strings -a ../jeff/target/release/dtk | grep -c __comdat_gap` still works as a spot check).
- **`config/373307D9/symbols.txt` is already a tracked ninja dependency** — editing it re-triggers SPLIT. This was tracked as an open task on the false belief that the wiring was missing; it has been there since the initial commit. Do not re-open it. See [docs/tools/BUILD_SYSTEM.md](docs/tools/BUILD_SYSTEM.md).
- **`dtk xex split` must not modify its own inputs** — its output has to be a fixed point of its input, or the depfile edge self-refires on every build. Test this after any splitter change (`docs/tools/BUILD_SYSTEM.md`). dtk's overlap check is correct: when it fires, fix whatever produced the overlapping symbols, and never hand-revert generated config to work around a generator bug.

For build-system details (the split graph, the fixed-point rule, toolchain propagation) see `./docs/tools/BUILD_SYSTEM.md`.

## Git Worktrees

Use `scripts/setup_worktree.sh <path> <branch>` to create worktrees with a working build system (configures ninja, symlinks tools/compilers/target objects) **and a configured native build, so `scripts/native_test.sh` runs with no manual steps**.

⚠ **The native gate was unrunnable in a worktree until 2026-08-31, and that is worse than an inconvenience.** `find_package(Dawn REQUIRED)` cannot find Dawn unaided — it is a pre-built dependency in the sibling repo `dc3-decomp-deps` — so every native configure needs `-DDawn_DIR=…`, and `setup_worktree.sh` had no configure step at all. `scripts/native_test.sh` died on `error: no configured build` before running one test; three lanes hit it in a day. Since a lane that gives up there has **examined zero tests**, and a bare `exit 1` reads like any other hiccup, the missing-build state is now **exit 8** under a "NATIVE GATE DID NOT RUN — this is NOT a pass" banner (see the full exit-code table in the script header: 2/3 ratchet, 4 unparseable summary, 5 disarmed budget, 6 build failed, 7 missing target list, 8 no configured build). Dawn was the reported symptom, not the set: the full delta between the main checkout's `native/build/CMakeCache.txt` and a bare worktree configure is `Dawn_DIR`, `ncnn_DIR`+`ENABLE_NCNN` (`native/third_party/` is gitignored — absence is silent, `find_package(ncnn QUIET)` just turns the feature off), `CMAKE_BUILD_TYPE=RelWithDebInfo`, clang as C/CXX compiler, the Ninja generator (`TestGates.BuildMatchesSources` interrogates ninja's real graph), and `CMAKE_EXPORT_COMPILE_COMMANDS`. All of it is derived — never hardcoded to `/home/free` — by `scripts/native_configure.sh`, which locates the main checkout with `git rev-parse --git-common-dir` (the idiom that fixed `MILO_ENGINE_PATH`'s worktree bug) and, when a genuinely external dependency is absent, exits **9** naming every path it probed. `scripts/check_native_compiles.sh` routes through the same script rather than carrying a second, subtly different configure line. The first `native_test.sh` in a new worktree still pays a full ~10-minute native build: a CMake build dir records absolute source paths, so reflinking main's `native/build` would make the worktree compile **main's** sources — gating the wrong tree.

**`decomp.db` does not exist in a worktree, on purpose.** A worktree `ninja` used to grow its own shadow DB — every row, **zero verdicts, zero percentages** — and every script defaulting to `--db decomp.db` then answered out of it. Identical work queries, measured 2026-08-19: AT_LIMIT certs `0` vs `3,796`; near-misses `0` vs `89`; the 80-95 band `0` vs `325`. An empty result reads as *"this class is exhausted"*. Three layers now stop that (fixed 2026-08-19):

- `setup_worktree.sh` plants a **tripwire** at `<worktree>/decomp.db` that is deliberately not a valid SQLite file, so *any* reader — including the ~50 scripts that call `sqlite3.connect()` directly — gets `file is not a database` instead of a plausible answer. `cat` it for the explanation.
- `orchestrator.database` raises **`ShadowDatabaseError`** naming both paths, and refuses to auto-create or auto-migrate a worktree-local DB.
- The ninja db-sync edge **skips** in a worktree rather than creating one.

From a worktree, pass the real DB explicitly: `--db /home/free/code/milohax/dc3-decomp/decomp.db`. The **MCP orchestrator tools are unaffected** — they resolve `decomp.db` against the server's own project root — so keep using `project_dir="<worktree>"`. `DC3_ALLOW_SHADOW_DB=1` is the escape hatch if you really do want a throwaway local DB.

## Shared Engine

DC3's native port consumes the shared **`../milo-native-engine`** repo (sibling at `/home/free/code/milohax/milo-native-engine`) — a game-agnostic LP64 modern-C++ runtime that owns gfx (WebGPU), audio (miniaudio/FFmpeg), input, file I/O, the host-STL shim, and POSIX impls of the `os/` interfaces. As of Phase 0, **all four native consumers — `dc3-native`, `milo-viewer`, `render-test`, `milo-tests` — link `libmilo-engine.a`** (built via `add_subdirectory(${MILO_ENGINE_PATH})`). ⚠ **Do not quote a test count from this file — measure it.** The suite grows every time a lane lands a regression test, and this paragraph has carried three different "current" figures in two days (445/371/74, then 449/380/380/0/69, then 504/434/434/0/70 on 2026-08-23), each of which read as fact while stale. Run `scripts/native_test.sh` and use what it prints. **A skip count that has moved is the signal**: it means coverage changed, and the ratchet exists to make you look — but *check the environment before you believe it*, see the two traps below. **Run `scripts/native_test.sh`, not bare `ctest`.** ⚠ **Two ways this measurement lied on 2026-08-23, both now closed.** (1) **The wrapper did not build.** It ran `ctest` and nothing else, so the main checkout's three-day-old `native/build` reported `449 registered / 380 executed / 380 passed / 0 failed / 69 skipped / exit 0` while a freshly built tree at the *same commit* registered **504**. The 55 missing tests were all added after the build; a test that does not exist cannot fail, so the run was green, and `TestGates` passed too because the gates it checks really were delivered — to a binary that was not this tree's. **The gate sets were identical in both trees** (`MILO_LIB`, `DC3_DTA_FLOW_TESTS` ON; `DC3_GAMEPLAY_TESTS`, `DC3_AUDIO_TESTS`, `MILO_LONG_TEST` OFF); this was **not** a `CMakeCache` shadowing bug like `MILO_ENGINE_PIN` — those two gates are not cache variables at all. The wrapper now builds first (exit 6 if the build fails), and `TestGates.BuildMatchesSources` asks ninja's real dependency graph whether the build is current. The target list lives in **one** place, `MILO_TEST_REQUIRED_TARGETS` in `native/CMakeLists.txt`, read by both the wrapper and the test — because the suite drives **three** binaries as subprocesses (`milo-tests`, `dc3-native`, `milo-viewer`) and each absent one removes its tests in a different disguise. `all` is not usable: **`wgpu-window-test` has not compiled since `gfx/GpuDevice.h` moved into the shared engine** (last built 2026-03-25, pre-existing, unfixed). (2) **The skip budget is only portable if `archive/` is.** `archive/` is gitignored, so `MiloViewerScreenshot.PoseDumpCanMatchGoldenWithTolerance` skips in every worktree and the count reads **70 vs a budget of 69 → exit 2, "coverage shrank"**, which it had not. `setup_worktree.sh` now symlinks `archive/` alongside `orig-assets`; the wrapper names the missing golden on exit 2. **Do not raise the budget for this.** `ctest` counts skips as passes and prints "100% tests passed" either way; the wrapper prints executed/passed/failed/**skipped** separately and enforces a ratchet against `native/tests/skip_budget.txt` (exit 2 if coverage shrank, exit 3 if it improved without the budget being locked in). ⚠ **That ratchet used to be disarmable by deleting or rewording its own budget file** — a missing `skip_budget.txt` exited **0** with the gate silently off, and so did rewriting it as `budget: 69`, which diffs like a doc improvement. Both now exit 5. Do not "fix" a skip regression by editing the budget; that is laundering, and the file is the evidence. `MILO_LIB` and `DC3_DTA_FLOW_TESTS` now default ON whenever CMake can prove the assets exist (that recovered 9 tests); `DC3_GAMEPLAY_TESTS` (48 tests, one ~2 min engine run), `DC3_AUDIO_TESTS` and `MILO_LONG_TEST` are still off by default — use `scripts/native_test.sh --all-gates`. The `TestGates` suite prints the gate table on every run and FAILS if a gate CMake enabled does not reach the test process. The older **371/371** figure was stale for a different reason (441 registered, 362 executing); the number coinciding again now is a coincidence.

The engine is pulled in with a soft SHA pin: `MILO_ENGINE_PIN` in **`native/CMakeLists.txt`** (currently `d62700c`); a mismatch with the engine's `git HEAD` warns but never fails. Bump it with `scripts/bump-engine.sh --apply`.

*History (2026-08-19, fixed):* the pin used to be `set(... CACHE STRING ...)` **without `FORCE`**, so `CMakeCache.txt` permanently shadowed the source value — the warning quoted the cached pin, not the one in the file, and `bump-engine.sh --apply` was a no-op against every existing build dir. Four values were live at once (engine HEAD, source `77eb428b`, cache `12455b0a`, this doc's `8282103`). The pin now carries `FORCE`, so the source always wins; `bump-engine.sh` **refuses to write** if someone removes `FORCE` again, and lists any build dir whose cached pin still disagrees. `MILO_ENGINE_PATH` deliberately keeps *no* `FORCE` (`-D` override must keep working) but its default now falls back to the main checkout's sibling via `git rev-parse --git-common-dir`, so it resolves correctly inside a worktree.
