# YMCA — Full DTA flow from boot to gameplay
#
# Navigates through the complete screen chain:
#   attract -> (auto) autosave_warning -> (auto) title
#   -> (auto) wait_main_after_saveload -> main -> choose_mode
#   -> song_select -> multiuser (difficulty, play, skip_waiting) -> loading
#   -> preloading -> real_loading -> game_screen
#
# Splash screens (ESRB/Harmonix logos) happen during App init before the
# UI screen system starts, so no input is needed to dismiss them.
# autosave_warning_screen and wait_main_after_saveload_screen auto-advance
# without input.
#
# IMPORTANT: +N offsets are all relative to the LAST wait_screen satisfaction
# frame, NOT to the previous directive. They must be monotonically increasing.
#
# NOTE: A HamNavList ignores buttons while its enter animation runs (~20 UI
# frames -- the image's HamNavList::OnMsg(ButtonDownMsg) checks IsAnimating()),
# so the first press on title/main/choose_mode waits +30.  With DC3_FAST_BOOT=1
# title_screen auto-advances after 60 frames, so its confirm must land before.
#
# Usage:
#   MILO_HEADLESS=1 MILO_FATAL_FAILS=0 \
#     MILO_MAX_FRAMES=5000 \
#     MILO_INPUT_SCRIPT=scripts/dc3-input-flows/ymca.txt \
#     native/build/dc3-native

# WAKE: on the 360 (and the original under Xenia, and native under
# DC3_CONTROLLER_MODE=faithful) a pad press outside controller mode does not
# act: ShellInput::OnMsg(ButtonDownMsg) swallows it and only enters controller
# mode, which lapses after controller_mode_timeout (5 s) with no pad input.
# `wake` = "the player presses the wake button" (l3): a no-op while the game is
# in controller mode -- always, under the native default
# DC3_CONTROLLER_MODE=forced -- else a one-frame press.  A no-op wake does not
# restart the idle timer, so each screen's first real press gets a wake 2
# frames ahead of it, never earlier.  No later gap on a screen reaches 5 s (the
# longest is ~120 frames), so no other press needs one.  See
# docs/debugging/native.md "Controller Mode Policy".

# attract_screen plays videos/intro.bik (83 s) since the desktop movie path
# opens movies out of the archive (PLAN G-15; until then it failed to open and
# the screen advanced on the first poll).  Skip it the way a player does: the
# overlay's SKIP item (movie_overlay_panel NAV_SELECT_MSG -> skip_selected ->
# autosave_warning_screen).  movie_overlay_panel's enter exits controller
# mode, so the confirm needs its wake.  Under DC3_FAST_BOOT the screen is gone
# after 10 frames and both presses land on autosave_warning_screen, which
# advances by itself either way.
wait_screen attract_screen
+28 wake
+30 confirm

# Press spacing is set for BOTH the native port and the original game under
# Xenia (xenia tools/fork-regress/flows/dc3-ymca.txt is this file). On the
# original, a menu list ignores confirms for ~0.55 s while its enter animation
# plays, a rejected press blocks the next ~1 s, and multiuser panes switch ~0.5 s
# later than native; native's +30 presses missed there. Hence +45 per menu and
# the wider multiuser spacing.

# autosave_warning_screen auto-transitions to title_screen.
# Title screen -- press confirm to proceed.
wait_screen title_screen
+43 wake
+45 confirm

# wait_main_after_saveload_screen auto-transitions to main_screen.
# Main screen -- select "gameplay" (first item).
wait_screen main_screen
+43 wake
+45 confirm

# Choose mode -- select "perform" (first item).
wait_screen choose_mode_screen
+43 wake
+45 confirm

# Song select -- ONE down, derived from the list, not tuned until green.
# In perform mode song_select.dta's enter handler runs
# `{right_hand.hnl scroll_to_index 2 2}` (focus_song_index 2, top_index 2), and
# the list (song_offer_provider, sort_with_headers TRUE) reads
#   0 playlists  1 random_song  2 song_tier_0  3 ymca  4 betteroffalone
#   5 thehustle  6 song_tier_1  7 starships ...
# Tier headers are NOT skipped by the d-pad: HamNavList::OnMsg only skips
# !IsActive rows, and NavListHeaderNode::IsActive is true whenever any child is
# (selecting one collapses the list to its headers).  So the cursor starts on
# song_tier_0 and one down lands on ymca.  The old four downs landed on the
# song_tier_1 HEADER; they only reached a song because OnMsg's ScrollDown edge
# carried an invented `- 1` that fired one row early and jumped the cursor
# over index 6 to starships (so this flow was playing starships, not ymca).
wait_screen song_select_screen
+43 wake
+45 down
+105 confirm

# multiuser_screen is driven by the controller, as on the 360: the focused
# list (right_hand_p1) is seldiff_pane -> confirm the highlighted difficulty;
# startgame_pane -> confirm `play` (ready); readywait_pane -> confirm
# `skip_waiting` -> start_game -> enter_gameplay.  Each pane change replays the
# list's enter animation (presses dropped meanwhile), hence the spacing.
wait_screen multiuser_screen
+38 wake
+40 confirm
+150 confirm
+270 confirm

# First-run move tutorial.  enter_gameplay's gate (ui/global.dta:230) is
# `{! {profile_mgr has_seen_tutorial kTutorialGeneral}}`, and
# ProfileMgr::HasSeenTutorial is
#     mTutorialsSeen & tutorial || mGlobalOptionsSaveState != kMetaProfileLoaded
# The second clause is the image's "persistence is broken, do not nag" escape
# hatch.  Native used to take it on every boot because nothing ever loaded the
# global-options cache, so the tutorial was suppressed; now that the cache is
# wired (SaveLoadManager::Init + CacheMgrNativeInit) it loads, and a fresh
# profile gets the tutorial the image shows -- ui/tutorial/tutorial.dta:1014-1109,
# inserted between multiuser_screen and loading_screen.
#   screen_0  dialog, confirm -> screen_1
#   screen_1  panel,  confirm -> screen_2
#   screen_2  panel,  confirm -> screen_3
#   screen_3  panel,  confirm -> screen_4
#   screen_4  dialog, enter marks kTutorialGeneral seen and re-runs
#             enter_gameplay; confirm -> loading_screen
# One wait_screen per tutorial screen, because each perform-it panel has its own
# accept window.  Measured on the wired engine (headless native, ~245 fps):
#   * a confirm ~70 or ~220 frames after the panel's Enter is DROPPED,
#   * a confirm ~470 frames after Enter advances it,
#   * with no confirm the panel auto-advances ~1900 frames after Enter.
# So the window is roughly [460, 1900] frames after Enter, and +600 lands in the
# middle of it while keeping the whole tutorial under the 5000-frame flow cap.
# (A single block of spaced confirms would need every offset measured against
# the same origin, and the panels' enters are not evenly spaced.)  If the
# tutorial never appears -- a profile that has already seen it, e.g. a second
# run against the same DC3_CACHE_DIR -- the first wait_screen simply never
# satisfies and the loading screens advance without any further input.
wait_screen tutorial_perform_it_screen_0
+38 wake
+45 confirm
wait_screen tutorial_perform_it_screen_1
+600 confirm
wait_screen tutorial_perform_it_screen_2
+600 confirm
wait_screen tutorial_perform_it_screen_3
+600 confirm
wait_screen tutorial_perform_it_screen_4
+45 confirm
