# m2c bctr/jump table fix

## Problem

The orchestrator's m2c pipeline was failing on functions with switch statements (e.g. `SongInfoAudioTypeToSym`). The error:

```
Found bctr instruction at <stdin> line 20, but the corresponding jump table is not provided.
```

Root cause: `objdiff_to_m2c.py` only emits the `.text` section (code instructions), not `.rdata` (data sections). When the assembly references a jump table symbol like `jumptable_820DBFA0`, m2c detects the symbol name but can't find the actual table entries, causing a hard failure with zero output.

Additional issues surfaced once the first error was fixed:
- `lbzx r0, r12, r4, ??_C@...` -- indexed memory ops were incorrectly converted to offset(base) format
- `add r12, r12, r0, ?Symbol@...` -- relocation symbols appended to register-only instructions
- `lwz r4, ?gNullStr, r11` -- symbol references as memory offsets
- `std`/`ld` (PPC64 doubleword) instructions missing from memory op conversion
- Several assertion crashes in m2c's IR pattern matching and stack analysis

## Changes

### m2c fork (`~/code/milohax/m2c`)

**`m2c/flow_graph.py`** -- bctr fallback when jump table data is missing. When a jump table symbol is detected but its data isn't in `asm_data.values`, PPC `bctr` is now converted to a ReturnNode (indirect tail call) instead of raising `DecompFailure`. Matches the existing behavior for bctr when no jump table name is found at all.

**`m2c/ir_pattern.py`** -- Catch `AssertionError` in `match_inputrefs` during IR pattern simplification. Failed stack location mappings are treated as non-matches instead of crashing the whole decompilation.

**`m2c/translate.py`** -- Two fixes:
- `get_stack_info`: `stwu` stack size detection uses conditional checks instead of hard asserts, so non-standard stack setups skip gracefully.
- `set_switch_expr`: Early return when node isn't a `SwitchNode` (happens after bctr-to-ReturnNode fallback).

### dc3-decomp (`tools/objdiff_to_m2c.py`)

**Indexed memory ops**: Moved `lwzx`, `lbzx`, `lhzx`, `lhax`, `lfsx`, `lfdx`, `stwx`, `stbx`, `sthx`, `stfsx`, `stfdx`, `lwbrx`, `lhbrx`, `stwbrx`, `sthbrx`, `lwarx`, `stwcx.` into a separate `indexed_memory_ops` set. These use 3-register format (`lbzx rD, rA, rB`) and should not be converted to offset(base). The 4th-arg relocation symbol is stripped.

**PPC64 doubleword ops**: Added `ld`, `std`, `ldu`, `stdu` to the `memory_ops` set for offset(base) conversion.

**Symbol offsets in memory ops**: When the offset field of a load/store is a symbol (not numeric), it's now quoted and given an `@l` suffix: `lwz r4, ?gNullStr, r11` becomes `lwz r4, "?gNullStr"@l(r11)`.

**General relocation stripping**: Added `_is_reloc_symbol()` helper that detects MSVC mangled names, merged symbols, labels, and quoted symbols. A catch-all at the end of `format_instruction` strips trailing relocation symbols that objdiff appends to many instruction types.

## Result

Before: m2c fails with `DecompFailure`, orchestrator gets `(m2c error: ...)`, agents get no starting point.

After: m2c produces partial but useful output with exit code 0:

```c
s32 SongInfoAudioTypeToSym(s32 arg0, u32 arg1, s32 arg_sp0, u32 arg_sp7C) {
    arg_sp7C = arg1;
    if (arg1 <= 0x12U) {
        // Error: assert state.branch_condition is not None or state.switch_control is not None
        // At instruction: bctr
        return arg0;
    }
    ?Fail@Debug@@QAAXPBDPAX@Z(&?TheDebug@@3VDebug@@A, ...);
    ??0Symbol@@QAA@PBD@Z(arg0, ?gNullStr@@3PBDB);
    return arg0;
}
```

The switch body is lost (no jump table data to reconstruct it), but the function structure, error path, and constructor call are all visible -- enough for an agent to use as a starting point.
