# Matching MSVC Anonymous Namespace Hashes in a Cross-Platform Decomp Build

**Date**: 2026-02-26
**Project**: Dance Central 3 (Xbox 360) decompilation
**Compiler**: Xbox 360 MSVC `c1xx.dll` v16.00.11886.00 (Visual Studio 2010 era)
**Build host**: Linux via [wibo](https://github.com/decompals/wibo) (Win32 PE loader)

---

## Background

MSVC decorates anonymous namespace symbols with a per-compilation hash: `?A0x<HASH>@@`. For example, a function `Foo` inside `namespace {}` in a file compiled on machine `MYPC` from path `c:\src\bar.cpp` might get mangled as `?Foo@?A0x3f2a1b9c@@YAXXZ`. The hash encodes the build environment — computer name and file path — so the same source compiled on a different machine or from a different path produces different decorated names.

In a decomp project, we need our compiled `.obj` files to link against original `.obj` files extracted from the retail binary. Mismatched anonymous namespace hashes cause unresolved symbols at link time and noise in binary diffing tools.

Our decomp has 91 `.obj` files containing anonymous namespace symbols. On investigation, 77 of these had hash mismatches against the originals.

## MSVC Anonymous Namespace Hash Algorithm

### SigForPbCb — The CRC-32 Primitive

The hash primitive is `SigForPbCb`, exported by `MSPDB*.DLL` (the PDB helper library). Full source is available in Microsoft's leaked PDB source at `langapi/shared/crc32.h`:

```c
// Reflected polynomial 0xEDB88320 (standard CRC-32)
// 256-entry static lookup table
inline DWORD SigForPbCb(PB pb, size_t cb, SIG sig) {
    while (cb--) {
        sig = crctab[(sig ^ (*pb++)) & 0xFF] ^ (sig >> 8);
    }
    return sig;
}
```

- `pb`: pointer to input bytes
- `cb`: byte count
- `sig`: initial CRC value (NOT always 0xFFFFFFFF — callers chain calls)
- Returns: updated CRC state

No final XOR. This is important — the output of one call feeds directly as the `sig` parameter of the next.

### The Three-Call Chain

Anonymous namespace hashes are generated by chaining three `SigForPbCb` calls:

```
h1 = SigForPbCb(computer_name, len(computer_name), 0xFFFFFFFF)
h2 = SigForPbCb(normalized_path, len(normalized_path), h1)
h3 = SigForPbCb("\x00", 1, h2)
```

The final `h3` is formatted as 8 lowercase hex digits in the mangled symbol: `?A0x{h3:08x}@@`.

### Inputs

**Computer name**: Retrieved via `GetComputerNameW` (Win32 API), converted to narrow string. Uppercase. This is the machine's NetBIOS name.

**Normalized path**: The source file path after canonicalization:
1. `_splitpath_s` to extract drive/dir/filename/ext
2. `_makepath_s(drive, dir, NULL, NULL)` to isolate the directory
3. `GetShortPathNameW` on the directory (converts to 8.3 short names on NTFS)
4. `_makepath_s(NULL, short_dir, filename, ext)` to reassemble
5. Filename portion is lowercased

### Reversibility

CRC-32 is reversible:
- `h3 → h2`: O(1) — undo the single `"\x00"` byte feed
- Multi-byte reversal (h2 → h1 given known path): O(n) — walk the CRC table backwards byte-by-byte
- This enabled us to work backwards from known original hashes to isolate unknown inputs

## Reverse Engineering c1xx.dll

### Target

`build/compilers/X360/16.00.11886.00/c1xx.dll` — the Xbox 360 C++ compiler frontend. PE32 i386, 1.7MB. Disassembled with `i686-w64-mingw32-objdump -d`.

### Call Chain

Traced from symbol table emission to the hash generation:

```
0x106124ba  Scope/symbol node handler
  → 0x105d3fc0  Anonymous namespace mangler
    → 0x105d2ffb  GetCurrentFilePath()            ← decides per-TU vs per-file
    → 0x105d3e12  BuildMangledSymbolName()
      → 0x105d32c1  InitComputerNameHash()         ← CRC32(name, 0xFFFFFFFF)
      → 0x105d2a41  EncodeHashToBase36()
      → 0x105d3258  EncodePathBytesIntoName()
      → 0x105d33d2  OptionalFileSpecificHash()     ← only if filePath != NULL
```

### IAT Imports

| IAT Slot | Function | Library | Purpose |
|----------|----------|---------|---------|
| `0x105011a0` | `SigForPbCb` | MSPDBXX.DLL | CRC-32 hashing (8 call sites) |
| `0x10501084` | `GetShortPathNameW` | KERNEL32 | 8.3 path conversion |
| `0x10501080` | `GetComputerNameW` | KERNEL32 | Build machine identity |
| `0x10501368` | `_splitpath_s` | MSVCR100 | Path decomposition |
| `0x105012dc` | `_makepath_s` | MSVCR100 | Path reassembly |

### Path Normalization (0x1064c9d3)

Canonicalizes a file path string through several layers:

1. **String interning** (`0x105e35ed`): Jenkins-like hash with LCG finalization
   - Init: `0xb170a1bf`
   - Per 4-byte chunk: `hash += *(uint32_t*)ptr; hash *= 0x401; hash ^= (hash >> 6)`
   - Per remaining byte: same with single byte
   - Finalize: `hash *= 0x19660d; hash += 0x3c6ef35f` (Knuth LCG)
   - Lookup/insert in hash table at `0x105e329c`

2. **Pointer-identity cache** (`0x105d8887`):
   - Keys: interned string **pointers** (address, not content)
   - Hash: `ptr * 0x19660d + 0x3c6ef35f`
   - Bucket: `hash % table_size`
   - Nodes: `struct { void* next; void* key_ptr; void* value; }` (12 bytes)
   - Lookup: walk chain comparing `node.key_ptr == search_ptr` (pointer equality)

3. **On cache miss**: splitpath → GetShortPathNameW(directory) → makepath → intern → cache

The pointer-identity cache means two strings with identical content but different interned addresses get separate cache entries. This is relevant to understanding path aliasing behavior.

### The Per-File Flag — Dead Code

The key function `GetCurrentFilePath()` at `0x105d2ffb`:

```c
char* GetCurrentFilePath() {
    void* ctx = g_currentContext;        // global at 0x106a4824
    if (ctx != NULL && g_perFileFlag) {  // g_perFileFlag at 0x10688aa9
        return getFileFromContext(ctx);   // returns HEADER file path
    }
    // Fallback: main TU (.cpp) path
    FileList* list = g_anotherFlag ? g_primaryFiles : g_secondaryFiles;
    return list->first->fileInfo->pathInfo->path;
}
```

**`g_perFileFlag` at `0x10688aa9` is permanently zero:**
- `.data` section offset: `0x10688aa9 - 0x10500000 = 0x188aa9` → raw file offset confirmed 0x00
- No write instructions reference this address anywhere in c1xx.dll (exhaustive scan of all `mov [addr]`, `mov [reg+disp]` encodings)
- Read at 4 locations (all `cmp byte ptr [0x10688aa9], 0` / `test` patterns)
- The "true" branch (`getFileFromContext` at `0x10605c73`) is dead code

**Implication**: This compiler version always uses the main translation unit's `.cpp` path for the anonymous namespace hash, regardless of which header file contains the `namespace {}`.

### Computer Name Hash Init (0x105d32c1)

```c
static uint32_t g_computerNameHash;  // 0x106a6f20
static uint8_t  g_hashInited;        // 0x106a6f24

uint32_t InitComputerNameHash(const char* name, int len) {
    if (!(g_hashInited & 1)) {
        g_hashInited |= 1;
    }
    g_computerNameHash = SigForPbCb(name, len, 0xFFFFFFFF);
    return g_computerNameHash;
}
```

Called once per compilation. The global is written but never read — callers use the return value.

### Prior Art / Public Research

- No public documentation exists for the anonymous namespace hash algorithm
- Clang's MSVC-compatible mode uses xxHash64, deliberately NOT matching MSVC's output
- LLVM review D50877 confirms MSVC uses absolute paths, Clang uses relative
- Quarkslab's XFG analysis of c1.dll is the closest public reverse engineering work, but covers XFG hashes (a security feature), not anonymous namespaces
- Geoff Chappell documents c1xx.dll command-line options but not internal hashing
- Microsoft's leaked PDB source (`microsoft-pdb`) contains `SigForPbCb` and `SzCanonFilename` but not the anonymous namespace logic itself (that lives in c1xx.dll, not the PDB libraries)

## The Shared-Hash Contradiction

If the compiler always uses the main `.cpp` path, each translation unit should produce a unique hash. But the original `.obj` files show:

| Hash | # Files | Source |
|------|---------|--------|
| `c9fefd64` | 55 | `Debug.h` (`AddToStrings`) |
| `b39b74bf` | 13 | DebugGraph-related header |
| `81ddebd1` | 5 | WaveFile-related header |
| `f8e4b4b5` | 4 | Unlockable-related header |
| `8ccc14d7` | 2 | gesture/stream header |
| `8e584365` | 2 | NUI camera header |
| `53f5bb0a` | 2 | DateTime header |
| (70 unique) | 1 each | Per-TU `.cpp` hashes |

55 different `.cpp` files cannot CRC-32 to the same value. The original build produced per-header hashes, but our compiler version's per-file code path is dead.

**Possible explanations:**
1. Different SDK version with `g_perFileFlag` enabled (Xbox 360 SDK had many patch levels)
2. Build system presented identical "main file" paths to the compiler (precompiled headers, response files)
3. The `.obj` files in `build/373307D9/obj/` were reconstructed by `dtk xex split` from the linked binary — the splitter may have normalized or merged anonymous namespace symbols
4. `GetShortPathNameW` on real NTFS returns 8.3 short names that could alias in the intern table's pointer-identity cache

## Solution: Three-Layer Fix

### Layer 1: Computer Name Hook — `WIBO_COMPUTER_NAME`

Brute-forced via meet-in-the-middle search against known original hashes. Found **`9QVZU3`** produces `CRC32("9QVZU3", 0xFFFFFFFF) = 0x9f6add5d` — the correct seed that, when chained with original paths, reproduces original hashes.

Wibo intercepts `GetComputerNameW` / `GetComputerNameA`:
```c
// dll/kernel32/kernel32.cpp
const char* envName = getenv("WIBO_COMPUTER_NAME");
if (envName) { /* return envName instead of gethostname() */ }
```

Build system integration — ninja passes it in every MSVC command:
```
WIBO_COMPUTER_NAME='9QVZU3' cl.exe /c /O1 ...
```

### Layer 2: Path Mapping — `WIBO_PATH_MAP`

The original build paths were `e:/lazer_build_gmc1/system/src/...` and `e:/lazer_build_gmc1/lazer/src/...`. We map these to local paths:

```python
# configure.py
config.wibo_path_map = (
    f"e:/lazer_build_gmc1/system/src/={Path('src/system').absolute()};"
    f"e:/lazer_build_gmc1/lazer/src/={Path('src/lazer').absolute()}"
)
```

Wibo translates paths at the `GetShortPathNameW` and file-open level. The compiler sees original Windows paths, so both `__FILE__` expansions and CRC-32 path hashes match.

**Side effect**: Also fixed `??_C@_` string literal hash mismatches. MSVC mangles string literals with a content hash that includes `__FILE__` — with correct paths, 121/121 string literal symbols matched.

These two layers fix the 8 per-TU hashes (where the anonymous namespace is in the `.cpp` file itself). The remaining 77 are header-sourced and need the patcher.

### Layer 3: Post-Build Binary Patcher

`scripts/obj_anon_ns_patcher.py` — 295-line Python script that patches compiled `.obj` files to replace decomp hashes with original hashes.

**Algorithm:**
1. Walk `build/373307D9/obj/` (original split `.obj` files) and `build/373307D9/src/` (decomp-compiled `.obj` files)
2. For each file, extract all `?A0x([0-9a-fA-F]{8})@@` patterns via regex on raw bytes
3. Build "common hash" set: any hash appearing in >5 original files is a shared header hash
4. Match decomp to original by relative path
5. Replacement logic:
   - 1 decomp hash, 1 original hash → direct binary replace
   - 1 decomp hash, N original hashes → filter common hashes; if 1 unique remains, replace with it
   - Otherwise → skip (ambiguous)
6. Binary find-and-replace: `?A0x{old}@@` → `?A0x{new}@@` (same length, safe for COFF)

The replacement is byte-level, touching only the 8 ASCII hex digits within the pattern. COFF symbol table entries and string table entries both use this same decorated name format, so a single find-and-replace catches all occurrences.

**Build integration** — runs automatically as a ninja post-compile step:

```python
# configure.py
config.custom_build_rules = [
    {"name": "run_script", "command": "$cmd && touch $out", "description": "$desc"},
]
config.custom_build_steps = {
    "post-compile": [
        {
            "outputs": str(stamp_dir / "anon_ns_patched.stamp"),
            "rule": "run_script",
            "order_only": "all_source",
            "variables": {
                "cmd": "python3 scripts/obj_anon_ns_patcher.py --batch --apply",
                "desc": "PATCH anonymous namespace hashes",
            },
        },
    ],
}
```

Ninja dependency chain:
```
[all .obj compilations] → all_source (phony)
                                ↓ (order_only)
                         anon_ns_patched.stamp (run_script)
                                ↓
                         post-compile (phony)
                                ↓ (order_only)
                         default.exe (msvc_link)
```
