# Bool Mask & rlwinm Fusion Analysis

**Date**: 2026-02-28

## Overview

Analysis of two related MSVC PPC codegen patterns affecting AT_LIMIT functions:

1. **Bool mask (`clrlwi` insert/delete)** — extra byte-truncation instructions at type boundaries
2. **rlwinm peephole fusion** — compiler fuses separate shift/mask/rotate instructions into combined `rlwinm` variants

Part 1 covers post-build patching feasibility. Part 2 covers deep compiler analysis of the fusion pattern using ByteGrinder as a test bed.

## The Pattern

The MSVC PowerPC compiler inserts `clrlwi` (Clear Left Word Immediate) at bool type boundaries:

```
Target (original):                    Our build (decomp):
  li     r29, 0x1                       li     r29, 0x1
  clrlwi r29, r29, 24    <- extra       bl     MetaPerformer::Current  <- no mask
  bl     MetaPerformer::Current
```

`clrlwi rX, rX, 24` = `rlwinm rX, rX, 0, 24, 31` -- zeros bits 0-23, keeps bits 24-31 (byte truncation).

Two directions:
- **Delete**: Our build has an extra `clrlwi` the target doesn't -- need to **remove** 4 bytes from .obj
- **Insert**: Target has a `clrlwi` we're missing -- need to **add** 4 bytes to .obj

## Why This Is Harder Than Regswap Patching

Regswap patching swaps 5-bit register field values in existing instructions. Same instruction count, same section size, same branch offsets. Trivial in-place edits.

Bool mask patching requires **inserting or deleting entire 4-byte instructions**, which causes cascading changes:

1. **Section size changes** -- `.text` COMDAT section grows/shrinks by 4 bytes per patch
2. **Branch fixups** -- every intra-function branch that crosses the edit point needs offset adjustment
3. **Relocation fixups** -- every relocation VA after the edit point shifts by +/-4
4. **No NOP shortcut** -- replacing `clrlwi` with `nop` still shows as a mismatch in objdiff

## Algorithm

```
1. Run objdiff JSON diff for the function
2. Find insert/delete entries where opcode is clrlwi/rlwinm with bool mask encoding
3. For each DELETE (our build has extra clrlwi):
   a. Compute section offset of the instruction
   b. Remove 4 bytes from section data
   c. Fix all intra-function branches crossing the deletion point
   d. Fix all relocation VAs after the deletion point (-4)
   e. Update section size (-4)
4. For each INSERT (target has clrlwi we're missing):
   a. Encode the clrlwi instruction word: rlwinm rA, rS, 0, N, 31
   b. Insert 4 bytes at the correct offset
   c. Fix branches crossing the insertion point
   d. Fix relocation VAs after the insertion point (+4)
   e. Update section size (+4)
5. Verify with objdiff; revert if regression
```

### Branch Fixup Rules

Only intra-function branches need fixing -- external `bl` calls have REL24 relocations (linker-resolved).

PPC branch types to handle:
- **I-form** (`b`, opcode 18, AA=0): 24-bit signed PC-relative in bits 6-29, shifted left 2
- **B-form** (`bc`/`beq`/`bne`/`bdnz`, opcode 16, AA=0): 14-bit signed PC-relative in bits 16-29, shifted left 2

For **deletion** at offset X:
- Branch at offset I < X, target I+D > X: displacement -= 4
- Branch at offset I > X, target I+D < X: displacement += 4
- Both on same side of X: no change

For **insertion** at offset X: reverse the signs.

To identify which branches are raw PC-relative (vs relocation-backed):
- Build a set of offsets that have relocations
- Only fix branches that are NOT at a relocation offset

## Existing Infrastructure

### `obj_regswap_patcher.py`
- `COFFPatcher` class: parses COFF headers, sections, symbols, relocations
- `resize_section()`: handles file-level offset shifting (section headers, symbol table, relocation tables)
- `apply_patches()`: format-aware register field swapping
- Missing: branch fixup, relocation VA adjustment within a section

### `obj_transplant_patcher.py`
- Copies entire original function into decomp .obj (nuclear option)
- Handles section resize via `COFFPatcher.resize_section()`
- Handles relocation remapping (translating symbol indices between COFF files)
- Limitation: requires same relocation count in both source and target
- Defeats decomp purpose: source code no longer corresponds to .obj binary

### `obj_anon_ns_patcher.py`
- Model for build integration: post-compile step with stamp file
- Batch mode with `--batch --apply`
- Already wired into `build.ninja` as `post-compile` dependency

### Observed mismatch patterns in bool_mask functions

From objdiff analysis of AT_LIMIT bool_mask functions:
- Most functions have bool_mask mixed with `diff_arg` (address relocation) and `replace` (other differences)
- Pure clrlwi-only insert/delete is rare
- Many cases involve positional shifts (clrlwi at different offset, different registers)

Example from `KnownIssues::OnToggleL` (80.3%):
```
[13] insert  (base):   clrlwi r10, r10, 24  @0x34   <- our build has this
[15] delete  (target): clrlwi r11, r10, 24  @0x38   <- target has this instead
```
Note: different destination register (r10 vs r11) and different offset -- requires combined regswap + bool_mask fix.

### Realistic impact

- Pure bool_mask patching: ~4 functions, ~500 bytes of match recovery
- Combined with regswap: maybe 8-10 functions, ~1,500 bytes
- The infrastructure (branch fixup engine) enables broader instruction-level patching

## Architecture Recommendation

Rather than a standalone bool_mask patcher, build a **general instruction-level patcher** with:

1. **Register swaps** (existing) -- field-level edits, no size change
2. **Instruction insert/delete** (new) -- requires branch fixup engine
3. **Opcode replacement** (future) -- e.g., `clrlslwi` vs `srwi`+`slwi`

The branch fixup engine is the critical building block that enables (2) and (3).

## Source-Level Fix Approaches (Alternative to Patching)

Before patching, source-level fixes are preferred:

- **Extract to local bool variable**: `bool x = expr;` forces compiler to mask at assignment
- **Explicit `(bool)` cast**: `(bool)(ptr != NULL)` triggers mask insertion
- **Restructure control flow**: `&&` chains vs `if/return` patterns affect mask generation
- **Type declarations**: `bool` vs `int` at variable declaration affects downstream masks

See `docs/decomp/patterns/fixable-bool-mask.md` and `docs/sessions/2026-02-04-bool-mask-getrefractenabled.md` for case studies.

# Part 2: rlwinm Fusion — Deep Compiler Analysis

## Discovery

While investigating bool_mask functions in `ByteGrinder.cpp`, a deeper pattern emerged. The ~64 `op*` functions in ByteGrinder are structurally identical (same shape, different constants), providing an ideal controlled experiment for compiler behavior analysis.

### The ByteGrinder op* Pattern

Most op14-op28 functions follow this template:

```cpp
DataNode opN(DataArray *msg) {
    u32 operand = msg->Int(1);
    u32 w = msg->Int(2);
    u32 w2 = (w & 0xFF) << 8;
    u32 w3 = (w2 & 0xFFFFFF00) | (w & 0xFF);
    return u8((w3 >> N) + operand);   // op14-op20: addition
    // or: return u8(w3 >> N ^ l);    // op21-op28: XOR
}
```

The key insight: `w3 = ((byte << 8) | byte)` creates a repeated-byte pattern. Then `u8(w3 >> N)` is mathematically equivalent to a **byte rotation**: `(byte >> N) | (byte << (8-N))`.

## The rlwinm Fusion Mismatch

The target and our compiler both recognize this rotation, but emit different instruction sequences:

### Target (separate instructions — 4 insns):
```asm
clrlwi  r11, r3, 24       ; byte = r3 & 0xFF
srwi    r10, r11, N        ; right = byte >> N
slwi    r11, r11, (8-N)    ; left = byte << (8-N)
or      r11, r10, r11      ; result = right | left
```

### Our build (fused instructions — 1-2 insns):
```asm
extrwi  r11, r3, (8-N), 24  ; = rlwinm r11, r3, (24+8-N), (32-(8-N)), 31
                              ; extracts (8-N) bits at position 24, right-justified
                              ; effectively: (r3 >> N) & mask, fusing mask+shift
```

The `extrwi` instruction computes the same result in a single cycle by encoding the mask, shift, and extract into one `rlwinm` encoding. This is a PPC backend peephole optimization — the compiler recognizes that separate mask+shift+shift+or can be expressed as a single rotate-and-mask.

## Systematic Verification

All functions in the series show the same pattern at exactly 86.8% match:

| Function | Operation | Shift | Target | Our build | Match |
|----------|-----------|-------|--------|-----------|-------|
| op14 | `(w3>>1)+op` | >>1 | clrlwi+srwi(1)+slwi(7)+or | extrwi(7,24) | 86.8% |
| op15 | `(w3>>2)+op` | >>2 | clrlwi+srwi(2)+slwi(6)+or | extrwi(6,24) | 86.8% |
| op16 | `(w3>>3)+op` | >>3 | clrlwi+srwi(3)+slwi(5)+or | extrwi(5,24) | 86.8% |
| op17 | `(w3>>4)+op` | >>4 | clrlwi+srwi(4)+slwi(4)+or | extrwi(4,24) | 86.8% |
| op18 | `(w3>>5)+op` | >>5 | clrlwi+srwi(5)+slwi(3)+or | extrwi(3,24) | 86.8% |
| op21 | `w3>>1 ^ l` | >>1 | same + bool_mask | extrwi + clrlslwi | 75.4% |
| op22 | `w3>>2 ^ l` | >>2 | same + bool_mask | extrwi + clrlslwi | 75.4% |
| op24 | `w3>>4 ^ l` | >>4 | same + bool_mask | extrwi + clrlslwi | 90.0% |

The XOR variants (op21-op28) are worse because the bool_mask pattern compounds with the fusion mismatch.

op51 is the only 100% match in the series — it uses a completely different code structure (pre-extracted byte with `u32 w = (u8)msg->Int(2)`, different operations, no repeated-byte pattern).

## Source-Level Experiments

### Experiment 1: Explicit u8 rotation
```cpp
u8 b = w3;
return u8(((b >> 1) | (b << 7)) + operand);
```
**Result: 77.1%** — WORSE. Introducing a u8 intermediate variable changed register allocation, causing a cascade of r28↔r29 swaps across the entire function. The compiler still fused the rotation into `clrlslwi`.

### Experiment 2: Explicit u32 byte mask
```cpp
u32 byte_val = w3 & 0xFF;
return u8((byte_val >> 1) + operand);
```
**Result: 86.8%** — No change. The explicit mask produced a separate `clrlwi` matching the target's instruction [17], but the compiler still fused the subsequent shift operations. Net: one mismatch fixed, core fusion unchanged.

### Experiment 3: u8 type for intermediate
```cpp
u8 byte_val = w3;
// ...
```
**Result: 79.3%** — WORSE. The u8 type triggered different register allocation and additional bool_mask insertions.

### Conclusion

The rlwinm fusion is a **deep PPC backend peephole optimization** that cannot be controlled from C++ source. The same source expression produces different instruction encodings because the optimizer's rotate-and-mask fusion pass makes different decisions than the original compilation. This is likely due to:

- Different intermediate representation state (inlining context, optimization pass ordering)
- Different compilation unit context affecting optimization heuristics
- Subtle differences in the optimizer's pattern matching (which rlwinm combinations it recognizes as fusible)

### Key Takeaways

1. **14 of 18 AT_LIMIT bool_mask functions** are ByteGrinder `op*` functions with unfixable rlwinm fusion
2. **Pure bool_mask insert/delete** (without fusion) is extremely rare — most cases either have fusion or mixed patterns
3. **Source-level fixes** are unreliable for bool_mask: type changes affect register allocation unpredictably
4. **Post-build patching** for pure clrlwi insert/delete is feasible but low-yield (~4 pure candidates)
5. **rlwinm fusion patching** would require opcode replacement (rewriting `extrwi` → `srwi+slwi+or`), which is significantly harder than bool_mask patching — it requires the branch fixup engine AND instruction insertion
6. The **branch fixup engine** (Part 1, Algorithm section) is the critical infrastructure that would enable both bool_mask and fusion patching
